# Refatorar o DeepSeek Universal Harness para um Actor/Event Tool Runtime

Você está trabalhando sobre o fork `suissa/deepseek-universal-harness`, derivado do `deepseek-ai/deepseek-harness`.

Antes de modificar qualquer código, analise profundamente a arquitetura existente, preservando seus princípios de `capability seams`, registries, providers, context services, tool catalog, lifecycle, dependency inversion e composição por plugins.

O objetivo desta refatoração é transformar o modelo atual de execução de tools em um modelo universal, orientado a Actors e eventos, sem acoplar uma Tool à linguagem do Agent e sem duplicar implementações por Agent.

## 1. Princípio arquitetural

A nova arquitetura deve considerar:

```text
Capability
    ↓
Tool Definition
    ↓
Actor
    ↓
Event Interface
    ↓
Execution
```

Um Agent nunca deve importar diretamente a implementação de uma Tool.

O Agent deve apenas referenciar uma Capability e emitir um evento de execução.

Exemplo conceitual:

```text
Agent
  ↓
search("product", { name: "notebook" })
  ↓
ToolRequest
  ↓
Actor Runtime
  ↓
Tool Actor
  ↓
ToolResult
  ↓
Agent
```

A implementação concreta da Tool pode estar escrita em qualquer linguagem:

```text
TypeScript
JavaScript
Python
Rust
Go
Zig
Haskell
WASM
etc.
```

A linguagem da implementação não deve fazer parte do contrato da Capability.

## 2. Tool não é uma função importável

Não implemente a arquitetura utilizando:

```ts
import tool from "..."
```

como mecanismo fundamental de execução.

Uma Tool deve ser tratada como uma Capability executável através de um contrato de eventos.

O Agent conhece:

```text
capability identity
input schema
output schema
permissions
effects
execution policy
```

mas não precisa conhecer:

```text
implementation language
module path
function symbol
runtime internals
process identity
```

A implementação deve ser resolvida pelo runtime.

## 3. Actor como unidade universal de execução

Toda Tool deve executar como um Actor.

O Actor deve possuir:

```text
identity
mailbox
execution state
lifecycle
capability binding
event handler
```

O runtime deve ser responsável por criar Actors conforme demanda.

Exemplo:

```text
search
  │
  ├── Actor #1
  ├── Actor #2
  ├── Actor #3
  └── ...
```

Se houver aumento de concorrência, novos Actors podem ser criados automaticamente.

Quando não houver mais trabalho e a política permitir, Actors efêmeros devem ser destruídos.

```text
load ↑
Actors ↑

load ↓
Actors ↓

idle
↓
destroy
```

Não criar um Agent Manager externo apenas para realizar esse scaling.

O runtime de Actors deve ser capaz de realizar essa função autonomamente.

## 4. Código da Tool deve ser compartilhado

Não criar uma cópia da implementação da Tool para cada Agent.

Um milhão de Agents utilizando:

```text
search
```

deve continuar referenciando a mesma Capability Definition e o mesmo Tool implementation source.

A arquitetura deve separar claramente:

```text
Tool Definition
```

de:

```text
Tool Execution
```

e:

```text
Actor Instance
```

A existência de múltiplas execuções não deve implicar duplicação conceitual da implementação.

Não confundir isso com isolamento físico de processos. O objetivo arquitetural é impedir que cada Agent possua sua própria cópia/import da Tool.

## 5. Event Interface

Criar uma interface de eventos tipada e independente do transporte.

O contrato deve permitir que o mesmo evento seja transportado por diferentes mecanismos:

```text
In-Memory Queue
Unix Socket
TCP
QUIC
NATS
outros transportes
```

O código da Tool não deve precisar conhecer o transporte.

A abstração deve ser:

```text
Event<T>
```

e o transporte deve ser uma implementação substituível.

Conceitualmente:

```text
              Event Interface
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   In-Memory         TCP          NATS
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                Actor Runtime
```

## 6. Eventos como efeitos

A chamada de uma Tool deve ser representada como um evento/efeito tipado.

Exemplo:

```json
{
  "type": "tool.execute",
  "capability": "search",
  "target": "product",
  "arguments": {
    "name": "notebook"
  }
}
```

O resultado também deve ser um evento:

```json
{
  "type": "tool.result",
  "capability": "search",
  "target": "product",
  "execution_id": "...",
  "result": {}
}
```

Também devem existir eventos de lifecycle quando necessários:

```text
tool.requested
tool.accepted
tool.started
tool.progress
tool.result
tool.completed
tool.failed
tool.cancelled
tool.expired
```

Os eventos devem ser tipados.

## 7. Execution State como Event Log

O estado de uma execução não deve depender exclusivamente de um objeto mutável em memória.

Uma execução deve poder ser representada como uma sequência de eventos:

```text
Execution
├── request
├── arguments
├── context
├── permission.check
├── execution.started
├── execution.progress
├── execution.result
├── execution.completed
└── execution.expired
```

O runtime deve permitir persistir esses eventos conforme a política configurada.

O estado lógico da execução deve poder ser reconstruído a partir dos eventos relevantes.

O sistema deve suportar políticas de retenção, por exemplo:

```yaml
retention:
  execution_state: 24h
  results: 10m
  audit_events: 90d
```

Não assumir que todos os eventos precisam permanecer indefinidamente.

## 8. Somente `mode` deve ser necessário para configurar uma Tool

Este é um requisito central.

Uma Tool deve poder ser declarada com uma configuração mínima equivalente a:

```yaml
mode: in-memory
```

ou:

```yaml
mode: tcp
```

ou:

```yaml
mode: nats
```

ou qualquer outro modo suportado pelo runtime.

O `mode` deve determinar automaticamente a estratégia de execução, transporte, lifecycle e runtime necessários.

Não exigir uma configuração extensa para cada Tool.

Evitar configurações como:

```yaml
runtime:
  transport:
  actor:
  queue:
  lifecycle:
  serializer:
  executor:
  worker:
  protocol:
```

quando essas informações puderem ser derivadas de `mode`.

A configuração deve ser declarativa e mínima.

## 9. Modes

Projetar o sistema para que `mode` seja extensível.

Exemplo inicial:

```text
in-memory
ipc
tcp
quic
nats
wasm
process
```

Não assumir que esses são os únicos modos possíveis.

O runtime deve possuir um registry de modes/providers.

Conceitualmente:

```text
Mode Registry
     │
     ├── in-memory
     ├── ipc
     ├── tcp
     ├── quic
     ├── nats
     ├── wasm
     └── process
```

Adicionar um novo modo não deve exigir alteração no Agent Loop.

## 10. Genericidade da Tool

Não criar funções especializadas como:

```text
searchProduct()
searchCustomer()
searchOrder()
searchSupplier()
```

quando todas representam a mesma operação semântica.

Preferir uma Capability genérica:

```text
search(target, parameters)
```

Exemplo:

```json
{
  "capability": "search",
  "target": "product",
  "parameters": {
    "name": "notebook"
  }
}
```

A especialização deve estar na configuração/semantic contract da Capability, não hardcoded na implementação.

O código deve permanecer genérico.

## 11. Não criar tabelas físicas por tipo de Tool

Se SQLite for utilizado para persistência local de execução, não criar automaticamente uma tabela diferente para cada operação:

```text
search_product
search_customer
search_order
```

Preferir estruturas genéricas:

```text
executions
events
results
```

O tipo semântico deve estar nos dados:

```text
event.type
capability
target
execution_id
```

e não necessariamente no nome da tabela.

Isso permite que a mesma infraestrutura suporte novas capabilities sem migrações estruturais constantes.

## 12. Compatibilidade com o padrão de Capability Seam do Harness

Preservar o princípio arquitetural existente do Harness:

```text
Capability Seam
      ↓
Provider
      ↓
Implementation
```

A nova arquitetura deve evoluir isso para:

```text
Capability Seam
      ↓
Actor Provider
      ↓
Event Transport
      ↓
Tool Actor
      ↓
Execution
```

O `ctx.tools` deve continuar sendo o ponto de composição/registro das Tools, mas seu papel deve evoluir para resolver capabilities e iniciar/encaminhar execuções através do Actor/Event Runtime.

Não espalhar lógica de transporte ou lifecycle pelo Agent Loop.

## 13. Agent Loop

O Agent Loop não deve conhecer:

```text
Python
Node.js
Rust
Zig
TCP
NATS
SQLite
process spawning
Actor pooling
```

O Agent Loop deve somente:

```text
resolve capability
→ create ToolRequest
→ emit event
→ await/consume ToolResult
```

Toda infraestrutura deve permanecer abaixo do seam.

## 14. Lifecycle

Cada execução deve possuir um `execution_id`.

Exemplo:

```text
ToolRequest
    ↓
execution_id
    ↓
Actor
    ↓
events
    ↓
result
```

O runtime deve controlar:

```text
creation
activation
execution
timeout
cancellation
completion
expiration
destruction
```

Quando o Actor não possuir mais trabalho e sua política permitir destruição:

```text
Actor
  ↓
idle
  ↓
dispose
```

O estado necessário para recuperação deve estar no event log ou storage configurado, e não depender exclusivamente da memória do Actor.

## 15. Horizontal scaling

O runtime deve ser desenhado para permitir scaling horizontal sem depender de um orchestrator específico.

A unidade de escala deve ser:

```text
Actor
```

e não:

```text
Agent
```

Uma mesma Capability pode ter múltiplas instâncias:

```text
Capability: search

Node A
 ├── Actor 1
 └── Actor 2

Node B
 ├── Actor 3
 ├── Actor 4
 └── Actor 5
```

O mecanismo de transporte deve permitir distribuir eventos quando o `mode` escolhido suportar execução distribuída.

O runtime deve evitar assumir que todo Actor está no mesmo processo ou na mesma máquina.

## 16. Zero knowledge entre Agent e Tool implementation

O Agent não deve conhecer detalhes da implementação.

O contrato deve ser:

```text
Agent
  → Capability
  → Event
  → Result
```

e não:

```text
Agent
  → Python module
  → Python function
```

ou:

```text
Agent
  → JS package
  → imported function
```

Essa separação é obrigatória.

## 17. Reuso cross-language

Uma única Capability deve poder ser utilizada por Agents escritos em diferentes linguagens.

Exemplo:

```text
TypeScript Agent
       │
       ▼
     search
       │
       ▼
 Python Tool Actor
```

e:

```text
Rust Agent
       │
       ▼
     search
       │
       ▼
 Python Tool Actor
```

e:

```text
Zig Agent
       │
       ▼
     search
       │
       ▼
 Python Tool Actor
```

Nenhum desses Agents deve precisar importar ou executar diretamente código Python.

## 18. Separar semântica, execução e transporte

Manter três níveis independentes:

```text
Semantic Layer
    ↓
Execution Layer
    ↓
Transport Layer
```

Semantic Layer:

```text
capability
target
arguments
schema
permissions
effects
```

Execution Layer:

```text
actor
execution
state
lifecycle
timeout
cancellation
```

Transport Layer:

```text
in-memory
ipc
tcp
quic
nats
...
```

Uma mudança de transporte não deve modificar a semântica da Tool.

Uma mudança de linguagem da implementação não deve modificar o Agent.

Uma mudança no Agent não deve modificar a Tool.

## 19. Configuração desejada

A configuração final deve poder chegar a algo próximo de:

```yaml
tools:
  search:
    mode: in-memory

  filesystem:
    mode: process

  remote-search:
    mode: nats
```

O objetivo é que `mode` seja o principal ponto de decisão arquitetural.

Quando não houver configuração adicional, o runtime deve aplicar defaults seguros e determinísticos.

Não exigir configuração manual de componentes que podem ser derivados do mode.

## 20. Backward compatibility

Antes de remover o modelo atual, identificar todas as dependências existentes em:

```text
ctx.tools
tool registry
tool execution
tool schemas
tool catalog
agent loop
extensions
plugins
subagents
MCP
```

Criar uma camada de compatibilidade quando necessário.

O objetivo é migrar progressivamente:

```text
Legacy Tool
     ↓
Adapter
     ↓
Tool Actor
     ↓
Event Interface
```

e não realizar uma ruptura desnecessária no restante do Harness.

## 21. Implementação no runtime Zig

O runtime de Actors deve ser implementado de maneira adequada para execução altamente concorrente e baixo overhead.

O runtime Zig deve ser responsável por:

```text
actor creation
actor mailbox
event dispatch
execution lifecycle
timeout
cancellation
idle detection
actor destruction
transport abstraction
```

Não criar um gerenciador central obrigatório para cada Actor.

Preferir estruturas distribuídas e event-driven.

O runtime deve permitir que Actors efêmeros sejam criados somente quando necessários e destruídos automaticamente quando não houver mais trabalho.

## 22. Critério fundamental de arquitetura

Ao implementar, sempre perguntar:

> "Isso precisa existir na Tool ou pode ser derivado do `mode`?"

Se puder ser derivado do `mode`, não criar configuração redundante.

Perguntar também:

> "Isso precisa ser conhecido pelo Agent ou pertence ao runtime?"

Se pertencer ao runtime, não expor ao Agent.

E:

> "Isso é semântica da Capability ou detalhe de execução?"

Se for detalhe de execução, não colocá-lo no contrato semântico.

## 23. Resultado esperado

A arquitetura final deve permitir:

```text
Agent
  ↓
Capability Reference
  ↓
Typed Tool Event
  ↓
Actor Runtime
  ↓
Tool Implementation
  ↓
Typed Tool Event
  ↓
Agent
```

com:

```text
• implementação reutilizável
• zero import direto entre Agent e Tool
• interoperabilidade entre linguagens
• Actor como unidade de execução
• lifecycle automático
• scaling automático
• Actors efêmeros
• eventos tipados
• eventos como efeitos
• execution state reconstruível
• retenção configurável
• transportes intercambiáveis
• capability seams preservados
• configuração mínima
• `mode` como principal configuração
```

Não introduza complexidade configurável que possa ser resolvida pelo runtime.

Não especialize a implementação da Tool para um domínio específico.

Não acople o Agent à linguagem da Tool.

Não crie um novo sistema paralelo ao mecanismo de capability seams do Harness.

E não implemente apenas uma abstração conceitual: faça a arquitetura funcionar de ponta a ponta, incluindo registry, event contract, actor lifecycle, execution state, mode resolution, transport abstraction e integração com o atual `ctx.tools`.
